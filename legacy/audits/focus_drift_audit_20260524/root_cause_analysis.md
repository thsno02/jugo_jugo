# 根因分析

`status`: `LOOP_DONE`
`decision`: `focus_drift_root_cause_identified`

## 简短答案

漂移的根因是：旧版 v1 系统把 `node` 设成生产对象，把主题覆盖设成规划框架，把版本束、采纳和视图构建设成质量门，把已采纳主题节点和覆盖完成设成交付成功。来源挖掘中确实出现过接近原子事实的观察，但这些观察在任务包中被压缩成主题节点生成。

## 1. 最早推动对象错位的文件/步骤

最早的关键错误在协议层。`KB_INIT_KNOWLEDGE_MINING_PROTOCOL.md` 要求创建节点版本束：`node.yaml`、`card.md`、`provenance.md`、`change.md`。这个结构看起来有知识卡和出处论证，但它们服务于节点，而不是独立的原子事实知识卡。

因此后续执行者即使写了知识卡，也是在写节点的展示卡，不是在生产事实知识卡。

## 2. 让主题覆盖压过原子事实可靠性的门禁/指标

旧版门禁主要验证：

- 版本束是否完整。
- 引用、出处论证、结构契约是否通过。
- 过度声称是否受控。
- 采纳和视图是否正确。
- 生成图和状态是否刷新。
- 覆盖是否推进。

缺失的是：

- 每个原子事实陈述是否单独存在。
- 每个陈述的证据是否足够。
- 事实类型是 `known_fact` 还是 `accepted_fact`。
- 适用范围是否被精确限定。
- 状态是否为 `draft`、`accepted` 或 `rejected`。

## 3. 任务包把挖掘压缩为规划/综合

多个规划任务包都把前序观察转成节点任务：

- origin/canon：生成有边界的 origin/canon 节点。
- vs RAG/write loop：生成 LLM Wiki vs RAG 的 artifact/workflow comparison 节点。
- risks/governance/provenance：生成 risks/governance/provenance 节点。
- implementation ecosystem：生成 implementation ecosystem 节点。
- evaluation/evidence：生成 evaluation/evidence 节点。

这些任务都不是“从一个来源中抽取 5-10 个原子事实候选，然后分别写草稿、出处论证和审计”。

## 4. 输出产物证明知识卡变成了中间综合件

旧版知识卡往往包含多段综合、多个概念关系、多个来源和多个边界说明。它们更像主题报告或枢纽页种子，而不是可读的原子事实知识卡。

这解释了用户指出的核心问题：知识卡本身不可读，像某种中间状态，而不是一个已经沉淀出来的 zet 风格知识卡。

## 5. 角色边界与上下文隔离的作用

主控 agent / 执行者的分工后来变得更严格，这本来是好事。但因为执行者的权威输入是任务包，而任务包已经把对象定义成节点，执行者的自治只能在错误框架内优化。

换句话说，上下文隔离防止了主控 agent 直接执行，但没有防止控制器把错误的生产对象写进任务包。

## 6. 为什么强校验落到了主题节点采纳

旧版系统把“可发布”理解为节点版本束可被采纳和构建视图。于是强校验落在引用、版本束、结构契约、视图、生成状态上。

原子事实知识卡需要的强校验不同：它要证明一个相对原子的事实陈述在某个适用范围内可被视为 `known_fact` 或 `accepted_fact`。这个证明不应是事后挑战，而应是 `事实 -> 草稿知识卡 -> 出处论证 -> 已采纳知识卡` 的生产过程。

## 7. 合理设计用错层级

以下设计本身不是错的：

- 出处论证。
- 引用审计。
- 变更记录。
- 影响分析。
- 边界管理。
- 技能进化。
- 采纳和视图构建。

问题是它们被接到了主题/节点层。下一版应该先把这些机制下沉到原子事实层，等基础足够稳，再让枢纽页、主题、聚类从原子事实知识卡中自然生长。

## 最终根因

根因链条如下：

1. 协议把 `node` 设成生产对象。
2. 控制面把主题覆盖设成规划目标。
3. 来源挖掘的自下而上观察没有被提升为独立原子事实知识卡。
4. 任务包把观察压缩成有边界的主题节点。
5. 执行者按任务包正常执行，生成节点版本束。
6. 审计、采纳和视图门禁验证的是节点发布。
7. 最终 QA 以 v1 主题骨架交付为成功。
8. 知识卡结构允许宽综合和 `References` / `Footnotes`，却没有强制最小原子事实契约。

因此，旧版不是“执行不努力”，而是“错误目标被完整执行”。
