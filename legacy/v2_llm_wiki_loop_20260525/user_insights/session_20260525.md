# 会话洞察：2026-05-25

## 用户明确要求

- 文档主语言应为中文。
- `llm_wiki` 不要做成隐藏文件夹，人类需要能方便审计。
- 旧版产物和错误版本应该进入 `legacy/`，并说明问题。
- 当前 KB 的核心目标是生产 LLM Wiki topic 的知识库，不是生产“如何设计 KB 的 topic”。
- 必须使用 `data/` 里的本地来源内容。
- 公司电脑网络 retrieve 可能受限；有限尝试即可，失败要记录并搁置，未来个人设备再重试。
- loop 需要自治运行，人类会离开电脑，不能依赖人类持续管理。
- main-agent 应该是决策者，不是执行者。
- 如果 main-agent 开始做具体来源挖掘、写卡、审计或采纳，说明流程或技能设计有问题，需要立刻干预。
- sub-agent 需要明确行为和 scope。
- 需要单独审计 context isolation、input/output 和 context leak。
- 需要单独审计为什么出现 loop focus drift，先找证据，再提假设，再用证据验证。
- 需要 dedicated `loop/` 文件夹保存循环控制面。
- 需要考虑 hook / tool / script，而不是每次由 main-agent 临场写 sub-agent prompt。
- 需要考虑 sub-agent 生命周期：哪些常驻，哪些阅后即焚。

## 知识卡设计判断

- 当前 loop 重点是生长 atomic card，后续 hub、topic、聚合不是当前重点。
- hub 的存在依赖 clustering；但当前阶段不做 clustering。
- atomic card 是相对概念，不是绝对不可分。
- atomic card 应该是可读的 zet 风格卡，不是中间状态、流程日志或审计记录。
- atomic card 需要强校验，因为默认是 facts。
- fact 分为 `known_fact` 和 `accepted_fact`。
- `known_fact` 类似几乎不变的事实。
- `accepted_fact` 类似当前被公认的流程、做法或结论。
- provenance / 出处论证不是事后 challenge，而是把事实做实的过程。
- provenance 最终应是整理后的可读文档，不是流水日志。
- 知识来自 paper、blog、X post、GitHub 等来源，但不保证 100% 正确，因此需要 provenance justify。
- 知识本身管理是混沌的；图谱、双链、link 是对知识关系的建模，不是对知识本身的建模。
- 知识粒度是核心难点之一。

## Markdown 和卡片格式要求

- `Footnotes` section 必须放在最后。
- `References` 应该提前，且位于 `Footnotes` 之前。
- 知识卡 schema 要简单。
- 最小字段保持：
  - `statement`
  - `fact_type: known_fact | accepted_fact`
  - `support`
  - `scope`
  - `status: draft | accepted | rejected`
- 不要一开始加入复杂 metadata。

## 对 agent loop 的偏好

- 用户更重视 bottom-up，从 atomic 到后续聚合。
- 用户不接受 top-down 主题骨架作为当前生产方式。
- 用户对“生产周期很长但产出很少”敏感，需要检查流程是否过重。
- 用户希望 sub-agent 作为 planner / worker，而 main-agent 保持上下文干净。
- 用户希望 loop 有 out-of-loop 的自治和反思能力。
- 用户希望审计能独立进行，不先读已有审计报告。
- 用户希望出现偏差时追问“从哪里开始理解错了”，需要保留偏差证据。

## 技术偏好与推断

- 用户倾向于把稳定角色边界预定义，而不是每次临场 prompt。
- 用户认为如果触发 sub-agent 仍靠 main-agent 写 prompt，本质区别不大。
- 用户认可 hook / script / tool 作为轻量控制层。
- 用户认为 Claude CLI 可能适合写作型 worker，因为写作智能水平可能更高。
- 用户希望 main-agent 能在有预定义 sub-agent 的情况下，仍能主动创造新 sub-agent 或修改已有 sub-agent，但要有边界和流程。

## 当前风险

- main-agent 容易把控制面设计当成实际 KB 生产。
- 文档如果过度复杂，会变得不可读。
- 如果 task packet 太宽，sub-agent 仍会发生 context leak。
- 如果没有 dispatcher/tool 层，main-agent 仍会临场写 prompt。
- 如果没有生命周期设计，sub-agent 会带着污染上下文继续工作。
