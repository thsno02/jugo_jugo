## 0. 导言（Intro）：LLM Wiki 的概念理解与框架定义

Karpathy 提出的 **LLM 维基【LLM Wiki】**，核心不是让 LLM 帮人写笔记，也不只是给 **检索增强生成【RAG, Retrieval-Augmented Generation】** 增加一个更好的检索层。它提出的是一种新的知识工作范式：**让 LLM 在原始资料【raw sources】和用户问题之间，持续维护一个可复利、可链接、可审计、可被人和 agent 共同消费的知识层。**

在普通 RAG 模式下，系统通常在用户提问时检索相关片段，再生成一次性答案。这个模式解决了“回答时能不能找到资料”的问题，但没有解决“知识能不能沉淀、复用、更新和治理”的问题。同一个需要综合多份材料的问题，下次再问时仍然要重新检索、重新拼接、重新解释。Karpathy 的 LLM Wiki vision，是在原始资料和用户问题之间增加一个由 LLM 持续维护的知识中间层：新资料进入时，LLM 不只是索引它，而是把它整理进已有知识结构，更新页面、补充链接、标记矛盾、形成增量，并把有价值的回答写回知识库。

因此，LLM Wiki 的基本心智模型可以概括为：

```text id="f23wzz"
原始资料【raw sources】
  -> LLM 维护的维基【LLM-maintained wiki】
  -> 查询与探索【query / exploration】
  -> 有价值的回答写回知识库【write-back】
```

这里的“维基”不是静态文档集合，而是一个持续演化的 **知识制品【knowledge artifact】**。它既能被人阅读，也能被 agent 检索、更新、链接和维护。更准确地说，LLM Wiki 的本体不是单纯的图数据库，也不是单纯的 markdown 文件夹，而是一组有边界、有来源、有结构、有链接、有生命周期的 **知识卡片 / 知识页面【knowledge cards / knowledge pages】**，以及围绕这些卡片持续运行的维护工作流。

本文采用的工作定义是：

> **LLM Wiki 是一个由 LLM / agent 持续维护的知识卡片系统。每个知识卡片是人类可读、agent 可操作、来源可追溯的知识对象；卡片之间通过链接、引用、标签、实体关系、主题关系和时间关系形成轻量知识图；系统通过持续的提取、定界、去重、融合、链接、审核和提升，把原始文档逐步转化为可复用的知识库。**

这个定义强调三点。

第一，LLM Wiki 的基本单位不是原始文档，而是经过定界的知识单元。长文档本身不适合直接作为长期知识库的基本单位，因为它过长、过粗、难以局部更新，也难以被 agent 稳定复用。LLM Wiki 需要把文档中的知识拆解、重组和提升为更小、更清晰、更可操作的知识卡片。

第二，LLM Wiki 可以使用图结构，但它不等同于传统 **知识图谱【KG, Knowledge Graph】**。图是它的组织方式之一：卡片是节点，链接、引用、主题归属、实体关系和冲突关系是边。但 LLM Wiki 的节点不是裸实体，而是带有解释、判断、证据、适用边界和维护状态的知识页面。因此，它比传统 KG 更适合人类阅读和语义理解，也比普通文档库更适合 agent 操作和持续维护。

第三，LLM Wiki 的核心价值不只是“生成知识”，而是“治理知识”。它需要处理哪些知识可信、哪些知识重复、哪些知识冲突、哪些知识只是候选、哪些知识可以提升为稳定层。也就是说，LLM Wiki 是一个 **知识生产与知识治理系统【knowledge production and governance system】**。

### 0.1 LLM Wiki 的五个核心属性

为了把 LLM Wiki 和普通摘要库、RAG 索引、知识图谱、个人笔记系统区分开，本文将 LLM Wiki 理解为同时具备五个核心属性的知识系统：**来源锚定【source-grounded】、结构约束【schema-constrained】、关系可链接【linkable / graphable】、版本可治理【versionable / auditable】、agent 可操作【agent-operable】。**

| 核心属性                               | 含义                                                                |
| ---------------------------------- | ----------------------------------------------------------------- |
| **来源锚定【source-grounded】**          | 每个知识卡片都应能追溯到原始资料，关键判断需要有来源、证据和适用上下文，避免知识库退化为不可验证的 LLM 生成文本。       |
| **结构约束【schema-constrained】**       | 卡片不是随意文本，而应遵守稳定结构，例如标题、核心判断、摘要、来源、边界、相关链接、状态等字段，使人和 agent 都能稳定消费。 |
| **关系可链接【linkable / graphable】**    | 卡片之间需要通过引用、主题、实体、相似、冲突、增量等关系形成网络；图结构是组织和查询视图，但卡片本身仍是知识承载单元。       |
| **版本可治理【versionable / auditable】** | 知识不是一次生成后固定不变，而需要有草稿、候选、稳定、废弃、待处理等状态，并记录变更、审核和提升过程。               |
| **agent 可操作【agent-operable】**      | agent 不只是读取卡片，还要能创建、更新、拆分、合并、补充来源、建立链接、标记冲突、执行检查，并把有价值回答写回知识库。    |

这五个属性共同定义了 LLM Wiki 的技术边界：它不是简单的文档摘要，也不是单纯的向量索引，而是一个可被 agent 长期维护、可被人持续消费、可被系统审计和演化的知识工作空间。

### 0.2 从文档库到知识库：agent 执行的知识编译操作

在这个框架下，真正需要解决的问题不是：

```text id="2xl2os"
如何让 LLM 总结一批文档？
```

而是：

```text id="1gajxv"
如何让 agent 从文档库中持续生产
可追溯、可链接、可审核、可演化、
可被人和 agent 共同消费的知识单元？
```

这里可以把 agent 的工作理解为一组 **知识编译操作【knowledge compilation operations】**，但它不一定对应 repo 中一个独立的系统层。所谓“编译”，指的是 agent 对原始文档执行的一系列知识加工动作，包括：

```text id="9n5dw9"
提取【extraction】
定界【scoping】
去重【deduplication】
融合【synthesis / fusion】
链接【interlinking】
比较【comparison】
冲突标记【conflict marking】
来源绑定【provenance binding】
状态判断【state assignment】
审核准备【audit preparation】
```

这些操作的目标，是把长文档、网页、论文、讨论串和实现资料，转化为更适合长期维护的知识卡片。原始文档保存事实来源；agent 负责从中抽取和组织知识；知识卡片承载可读、可查、可链接、可审核的中间成果；人负责消费、检查和做关键提升决策。

因此，这里的核心不是“增加一个 compilation layer”，而是明确：**从文档库到知识库的转化过程，需要由 agent 持续执行一组知识编译操作。**

### 0.3 LLM Wiki 与 RAG、知识图谱的边界

从系统位置上看，LLM Wiki 处在 RAG、知识图谱和文档库之间，但不等同于其中任何一个。

与 **RAG【Retrieval-Augmented Generation】** 相比，LLM Wiki 不只是查询时检索，而是把知识提前沉淀为可复用的中间层。RAG 更关注“回答时找什么上下文”，LLM Wiki 更关注“知识如何长期存在、更新和复利”。

与 **知识图谱【Knowledge Graph】** 相比，LLM Wiki 可以使用图，但它的节点不是纯实体，而是带解释和证据的知识卡片。知识图谱更擅长结构化关系查询，LLM Wiki 更擅长人类可读的综合理解、判断沉淀和长期维护。

与普通 **文档库【document repository】** 相比，LLM Wiki 不是把资料存起来，而是把资料转化为可消费、可连接、可治理的知识单元。文档库保存原始材料，LLM Wiki 维护经过整理、链接和治理的知识层。

更完整的关系可以表示为：

```text id="jugrm8"
文档库【doc base】
  保存原始资料，是事实来源

RAG / 搜索层【retrieval layer】
  帮助系统找到相关材料或卡片

知识图谱 / 关系图【KG / relation graph】
  表达实体、主题、引用、冲突、相似和增量关系

LLM Wiki
  把资料、检索结果和关系结构组织为
  人类可读、agent 可操作、可持续治理的知识层
```

因此，LLM Wiki 的先进性不在于替代 RAG 或知识图谱，而在于把它们纳入一个更高层的知识治理框架中。RAG 可以作为检索工具，知识图谱可以作为关系索引，markdown wiki 可以作为人类可读界面，agent 则负责把这些能力连接成持续运转的知识生产系统。
