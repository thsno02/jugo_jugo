# V0-V1 审计机制演化证据审计

## 结论摘要

V0 已有审计契约、结构校验、引用图和 impact hold，但其正常路径把生成、`audit_result: passed`、`version_status: adopted` 与 root metadata 写入耦合在同一个 bootstrap 脚本中。它验证了“文件束是否完整、路径是否存在、引用是否可解析”，却没有验证“正在生产的是否是用户要的 LLM Wiki topic 知识”。因此 V0 的局部审计通过与产品目标失败同时成立：`codex:codex-primary-v0-v2-boundary:H002` 报告 7 个 adopted nodes 和 35 条引用边，`codex:codex-primary-v0-v2-boundary:H007` 随即由用户指出 topic object 错成了 KB 生产机制本身。

V1 把审计推进为可重放的逐节点链：candidate version bundle 先保持未采纳，独立 audit worker 给出 `adopt_recommended`、`repair_before_adoption` 等 verdict，必要时 repair/re-audit，最后才由 adoption/view worker 写 root metadata、KB view 和 generated state。首个 origin/canon 节点真实经历了“发现 X/HN 文件状态声明错误 -> repair -> re-audit -> adopt”；footnote layout 也真实阻断过采纳。但 V1 的合同仍以 versioned topic node、topic coverage 和 release mechanics 为中心。最终 QA 的 `v1_delivered` 只证明该合同下 8 nodes、16 cards/views、185 edges 的发布链通过；`codex:codex-primary-v0-v2-boundary:H017` 至 `codex:codex-primary-v0-v2-boundary:H024` 又由用户明确反证其不是 bottom-up atomic KB，生产周期过长，card 不原子且不可读。

按稳定阶段衡量，V0-V1 已形成 `audit-contract -> mechanical-filter -> semantic judge -> verdict -> local repair` 的雏形，但没有 V5 式可证明的 suspect shard ledger，也没有独立 fusion 或 cross-source leakage gate。真正的 adversarial probe 主要来自用户在交付后的具体质疑；V1 的证据驱动 root-cause audit 也是在产品目标被否定后才执行。V1 内的逐节点 repair 成功，不能当作对“错误产品目标”的修复证明。

## 证据口径

- **specified**：规则写入 plan、skill、gate 或 task，但没有足够证据证明在原运行中完整执行。
- **executed**：归档事件明确报告动作，且当前仓库存在对应 run artifact。事件是用户锚定的助手窗口摘要，不是逐命令原始日志。
- **observed_failure/contradicted**：运行产物、后续用户输入或独立审计直接否定先前状态、结论或目标。
- **retrospective**：后续归档、独立审计、README/status 或本次只读核对确认的终态与解释；不得倒写为原运行当时已具备的能力。
- 当前路径均为仓库相对路径。`loops/v0_meta_kb_initialization_demo_20260524/manifest.json` 与 `loops/v1_topic_hub_skeleton_20260524/manifest.json` 是后续 capsule 状态；`README.md`、`status.json` 和后来的设计/审计文档只能说明归档与事后判断，不能单独证明早期执行顺序。
- 稳定阶段名称沿用当前审计模块：`audit-contract`、`mechanical-filter`、`shard-judge`、`synthesize-verdict`、`adversarial-probe`、`root-cause-audit`、`remediation-experiment`。这里审计历史是否达到这些阶段，不用后来的命名包装当时不存在的流程。

## 关键演化判断

1. **V0 的核心问题不是“完全没有 audit”，而是 audit 与 adoption 耦合且合同漏掉 topic object。** 同一脚本预先写 `version_status: adopted`、`audit.state: passed`、root metadata、provenance 中的 adoption rationale 和 run audit report。结构校验是真实执行，产品对象失败也是真实反证；二者不可互相抹除。
2. **V1 的核心进步是逐节点状态机和可执行 repair。** origin/canon 的错误文件状态被 audit 捕获，candidate 保持未采纳，repair 后 re-audit，再由 adoption worker 发布；footnote layout 也阻断过一次已有 adopt recommendation 的候选。这些是 V1 最强的原运行证据。
3. **V1 的核心局限是把强审计接在了错误层级。** gates、provenance、citation、change、view 和 graph 都围绕 topic node release。最终 QA 的 pass 对旧合同有效，但用户后续否定的是合同没有度量的 atomicity、readability、bottom-up production 与 cycle cost。
4. **后续 root-cause 文档只能证明事后理解。** `loops/v1_topic_hub_skeleton_20260524/audits/focus_drift_audit_20260524/` 与 `context_isolation_audit_20260524/` 提供了强 retrospective evidence；不能据此声称 V0 bootstrap 或 V1 per-node audit 在交付前已经检查 focus drift、knowledge depth 或 context leakage。
5. **V1 的局部修复成功不等于产品修复成功。** source-state、layout、metadata 与 generated state 均有 repair/refresh 证据；用户拒绝产品目标后，新的 provenance-backed atomic/zet-card 契约只被讨论、归档和形成 recommendation，V1 内没有完成新的 remediation experiment。
