# V0-V1 入库机制证据审计

## 1. 审计边界与判定口径

本文只审计 LLM Wiki v0-v1 当时可证明的知识入库机制。稳定阶段名 `source-route/acquisition`、`questioning-extraction`、`reframe-drafts/topic production`、`scripted-ingest/promotion`、`fusion-decision`、`graph-governance`、`publish-kb`、`failure-feedback` 仅作为跨版本对照坐标，不表示 v0/v1 当时已经使用这些术语或具有后续版本的同名实现。

四类证据状态定义如下：

- **specified（已规定）**：动作发生前或同时期的 plan、protocol、skill、task packet 明确要求该机制。
- **executed（已执行）**：primary event、run artifact、产物终态或代码可直接证明动作发生。
- **retrospective（后验）**：归档 README、后验审计、版本注册表或用户追问后形成的解释，只能解释历史，不能替代当时执行证据。
- **contradicted（被反证）**：后续用户纠正、一手 artifact 冲突或 Git 边界推翻了先前的完成、范围或质量主张。

事件短名：`R01`-`R09` 指 `codex:codex-prehistory-research:H001`-`H009`；`P01`-`P31` 指 `codex:codex-primary-v0-v2-boundary:H001`-`H031`。事件文件保存的是 user verbatim 加 reviewed assistant summary；它可证明用户触发、当时公开回应和被报告的效果，但不是完整工具调用或 sub-agent transcript。【证据：`docs/claude_interaction_replay/events/events.codex.prehistory-research.v2.jsonl`；`docs/claude_interaction_replay/events/events.codex.primary-v0-v1.v2.jsonl`】

Git 只能证明某个 snapshot 何时进入版本控制。v0/v1 capsule 首次整体进入 Git 晚于其 run artifact 的声明时间，因此 Git 不能恢复每个 v1 worker run 的精确先后写入过程。【证据：Git `3fb7fa3831957a6b29db5ea096282d9ddea7aa14`；`loops/v1_topic_hub_skeleton_20260524/llm_wiki_runtime/runs/`】

## 2. 总结结论

可证实的演化链是：**前史采集建立 raw knowledge database 与 coverage-driven research records → v0 用既有本地证据和一次受控动态检索，直接生成并采纳 7 个“KB 生产机制”节点 → 用户指出 topic 对象错误后归档 v0 → v1 把 `data/` 设为主要证据层，按 source mining、frontier、node planning、candidate bundle、audit/repair、adoption/view build 的重型循环生成 8 个 LLM Wiki 主题节点 → 用户进一步指出它仍然违背 bottom-up atomic card 目标，v1 被降级为 topic hub skeleton。**【证据：`R09`；`P02`；`P07`-`P09`；`P12`-`P18`；`loops/v0_meta_kb_initialization_demo_20260524/README.md`；`loops/v1_topic_hub_skeleton_20260524/README.md`】

v0 的机制 demo 在其自身范围内真实运行：7 个 adopted 1.0 nodes、7 个 KB views、35 条 citation edges、1 个未采纳 major 2.0 candidate 和 4 个开放 impact entries 均有 artifact 支撑。但“机制运行”不能改写为“LLM Wiki topic KB 已正确入库”；`P07`、`P08` 明确反证了对象层成功。【证据：`P02`；`P07`；`P08`；`loops/v0_meta_kb_initialization_demo_20260524/generated/status.yaml`；`loops/v0_meta_kb_initialization_demo_20260524/kb_initialization_demo_report.md`】

v1 的 8 个 topic nodes、8 个 KB views 和 185 条 citation edges 也真实存在，candidate 与 adopted view 的边界比 v0 清楚。但 v1 的 source-backed observations 被压缩进预设 topic node，强校验落在 bundle/citation/layout/adoption/view，而不是用户后来重申的 atomic fact 生产对象；因此它是“错误目标被完整执行”，不是未执行。【证据：`P16`-`P24`；`loops/v1_topic_hub_skeleton_20260524/generated/status.yaml`；`loops/v1_topic_hub_skeleton_20260524/audits/focus_drift_audit_20260524/root_cause_analysis.md`】

v0/v1 均没有可证明的逐轮 questioning 记录、独立 reframing 阶段、跨草稿 fusion decision ledger，也没有名为 `ingest.py` 的入库脚本。v0 的生成脚本直接写 adopted metadata；v1 的 promotion 是 worker 在 audit pass 后更新 adoption metadata，再调用 deterministic view/graph scripts。不得用 v2+ 的 questioning、reframe、fusion 或 ingest 实现倒写 v0/v1。【证据：`scripts/kb_bootstrap_demo.py`；`scripts/kb_build_view.py`；`loops/v1_topic_hub_skeleton_20260524/llm_wiki_runtime/skills/llmwiki-source-mining/SKILL.md`；`loops/v1_topic_hub_skeleton_20260524/llm_wiki_runtime/skills/llmwiki-view-building/SKILL.md`】
